# M8.1 问题台账生命周期可视化与批量处置 — 设计文档

- 阶段：核心版体验切片（合并原 backlog「M8.1 批量处置」与「台账生命周期可视化」）
- 日期：2026-08-05
- 状态：待评审
- 前置：M6 问题台账（`issue-ledger-m6.md`）、M8 问题生命周期（`issue-lifecycle-m8.md`）、生命周期轮次事件落库（2026-08-05 已交付：`DETECTED`/`ROUND_HIT`/`ROUND_MISS` 三类事件写入 `review_issue_action`）

## 0. 目标与成功指标

### 业务目标

M8 的闭环逻辑完整但不可见：列表是平铺台账，状态只是生命周期的一个瞬时点；轮次轨迹（哪轮发现、跨了几轮、滞留多久）在字段里但没展示；单条处置要逐个开抽屉，积压后处置效率低。本切片让生命线「列表表面自明、详情完整可溯」，并开放批量处置。

### 成功指标

1. 不打开抽屉，列表可读：每个问题当前阶段、滞留时长、轮次轨迹一眼可见；
2. 页面顶部总览条给出状态分布与「需处理」计数，可截图进周报；
3. 详情抽屉生命线完整呈现「发现 → 命中/未命中 → 处置 → 关闭」全轨迹（事件数据已由前置落库）；
4. 勾选多个问题一次处置，无需逐条开抽屉；
5. 零 DDL、零新表、零新菜单、零新权限点（全部复用既有资产）。

### 明确不含

- 看板视图：问题状态由系统对账驱动而非人工拖拽，看板交互是伪需求；
- 按审查轮次分组视图：问题跨轮存活（family 语义），按轮分组会重复/分裂同一问题。「哪次审查有什么问题」用双向跳转解决——轮次→问题已有（审查记录重点问题区「台账」链接），问题→轮次由本切片轮次轨迹列补齐；
- 健康度统计页（关闭率、平均滞留时长）：治理场景，确有管理诉求再立切片；
- 严重级别差异化策略、inline 评论、质量门禁影子：roadmap backlog 其余项，不混入本切片。

## 3. 列表层设计

### 3.1 状态总览条（表格上方，常驻）

```text
┌──────────────────────────────────────────────────────────────┐
│ 待确认 3 ｜ 待修复 5 ｜ 待复核 2 ║ 需处理 5 ║ 累计已关闭 12   │
└──────────────────────────────────────────────────────────────┘
```

- 每个数字可点击 = 快捷筛选（等效选中对应 status）；「需处理」= 待确认 + 待复核 复合筛选（新增 `pendingOnly` 查询参数，与 status 下拉互斥，选了 status 时 status 优先，与现有 activeFlag 优先级规则一致）；
- 计数与列表同口径 DataScope；数字为 0 也展示（保留版式稳定）；
- 不做图表、不做趋势——结论数字 + 点击筛选足够，避免过度设计。

### 3.2 表格列

| 列 | 变化 | 说明 |
|---|---|---|
| 勾选框 | 新增 | 批量处置入口，表头全选 = 当前页（不做跨页选择） |
| 项目名称 | 保持 | 不新增业务系统列——项目名已可识别归属，控制列数；确有诉求后续加 |
| 合并请求 | 保持 | |
| 问题标题 | 保持 | |
| 严重度 | 保持 | |
| 阶段 | **升级自「状态」** | 状态 tag + 滞留时长：`●待修复 · 3天`；<24h 显示小时；进入阶段时间 = 该问题最后一条 `from_status != to_status` 的 action 时间，无则回退 `create_time`（新问题出生即待确认） |
| 轮次轨迹 | **新增** | `#2 → #5 · 未命中3`：发现轮（first_task_id）→ 最近命中轮（last_task_id）均可点击跳审查记录；未命中数为 missed_streak（0 时省略该段） |
| 归属 | 保持 | NEW/EXISTING |
| 更新时间 | 保持 | 默认排序仍 update_time 倒序 |
| 操作 | 保持 | 详情 / 复核（RECHECKING） |

### 3.3 批量处置（原 M8.1）

- 勾选后表格上方出现批量操作条：`已选 n 项 ｜ 确认 · 关闭 · 忽略 · 误报 ｜ 清除选择`；
- 按钮可用规则（全有或全无，不做部分执行）：选中集全部满足该动作前置态才可用，否则禁用并 tooltip 说明「选中项含不可确认的问题（n 项）」。前置态与单条状态机一致：
  - 确认：仅 AWAITING_CONFIRM；
  - 关闭：AWAITING_CONFIRM / AWAITING_FIX / RECHECKING（RECHECKING 关闭即「确认已修复」，close_source 规则与单条一致）；
  - 忽略 / 误报：同关闭三态；原因必填，弹窗输入后统一应用到本批（与单条驳回类必填规则一致）。
- 关闭/忽略/误报弹窗复用单条弹窗文案，标题改为批量口吻（「关闭 3 个问题」）；
- 执行结果：`已成功处理 n 项` 提示 + 刷新列表与总览条；部分失败（数据范围/状态竞态）返回明细，逐条列出未处理项与原因。

## 4. 详情抽屉：生命线升级

### 4.1 顶部生命线进度条

```text
发现 ●──── 确认 ●──── 待修复 ●──── 待复核 ○──── 关闭 ○
08-05 #2   08-05       08-05
```

- 节点：发现 → 确认 → 待修复 → 待复核 → 终态；终态节点文案随实际终态显示（已关闭 / 已忽略 / 误报）；
- 已达节点实心、当前节点高亮、未达空心；**跳过的节点保持空心不补实**（如未确认直接关闭：发现 ● ─ 确认 ○ ─ … ─ 已关闭 ●），如实呈现路径；
- 节点下小字标时间（发现节点附轮次任务号）；数据全部取自已有的 action 流水与 issue 字段，无新数据源。

### 4.2 时间线渲染优化

- 轮次事件已落库，沿用现有 el-timeline 通用渲染；
- 一处小优化：`from_status == to_status` 的事件（DETECTED/ROUND_HIT/ROUND_MISS）不再渲染「待修复 → 待修复」状态对，只显示事件名 + note + 时间；状态变化事件照常渲染状态对；
- 其余区块（定位/建议/证据/复核证据/投递）不动。

## 5. 工作台与路由联动

- 工作台卡片与跳转参数不变（`/review/issue?status=RECHECKING` 等既有链路保持）；
- 总览条筛选与路由 query 回填兼容：`status`/`pendingOnly` 纳入现有 `applyRouteQuery` 体系。

## 6. 接口与数据变更清单

| # | 变更 | 说明 |
|---|---|---|
| 1 | `GET /review/issue/stats` 新增 | 返回 待确认/待修复/待复核/需处理/累计已关闭 五计数；与列表同口径 DataScope；权限复用 `review:issue:list` |
| 2 | 列表接口出参补 `stageEnteredTime` | mapper 子查询：`COALESCE(MAX(action.create_time WHERE from_status != to_status), i.create_time)`；`idx_issue_id` 已有，分页内规模可接受 |
| 3 | 列表接口入参补 `pendingOnly` | `status IN ('AWAITING_CONFIRM','RECHECKING')`；与 status 互斥 |
| 4 | `POST /review/issue/batch` 新增 | body：`action`（CONFIRM/CLOSE/DISMISS）、`issueIds`、`resolveNote`、`dismissType`；事务内逐条校验数据范围与前置态，写 action 流水；**PR 总结评论按 projectId+prNumber 去重后每 PR 仅重渲染一次**；权限复用 `review:issue:confirm`/`review:issue:close` |

零 DDL：不改表结构，不加列，不动字典（action_type 前端常量映射已含三类轮次事件）。

## 9. 决策记录（产品判断，可推翻）

1. **不做跨页选择**：企业场景以筛选后按页处置为主，跨页选择的状态管理成本与误操作风险不成比例；
2. **批量不做部分执行**：选中集含不满足前置态的问题时整批禁用并提示，行为可预期，避免半成功状态的解释成本；
3. **列表不加业务系统列**：项目名已承载归属识别，列数克制；与投递记录页（已加业务系统列）的差异来自两页的列密度不同；
4. **滞留时长取「最后状态变更」而非 update_time**：轮次命中会刷新 update_time，不能代表状态滞留；action 子查询口径准确且数据已就位；
5. **进度条不补实跳过节点**：如实呈现处置路径（直接关闭也是合法路径），不制造「走过全流程」的假象。
