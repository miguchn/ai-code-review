# 数据洞察模块（Data Insights）设计

- 状态：**定稿待审**（2026-08-10）
- 上游依据：`product-roadmap.md` §4.2（数据洞察一级菜单）、§5（工作台/看板/报告分工）、§1.3/§2.2（非目标与绩效红线）、§5.2（首批指标定义）
- 数据基线：2026-08-10 平台数据分析报告（dev 联调数据 24 任务 / 54 问题 / 17 投递，度量口径已跑通）

---

## 1. 背景与目标

M1–M11 建成了审查闭环的事实层（事件、任务、问题、投递、处置动作全落库），但「为什么变化、谁在变、变得怎样」没有答案：管理者看不到覆盖与整改趋势，项目负责人看不到本项目的质量走向，成员看不到自己的变更被审查的情况。路线图 §5 已定分工：**工作台管「今天做什么」，看板管「为什么变化」，报告管「冻结并传播」**。本模块落地「看板」层。

目标：新增「数据洞察」一级菜单，提供平台总览、项目分析、成员分析三类看板，指标口径统一、权限隔离、可分阶段演进到报告中心。

## 2. 功能边界（对抗式复核）

### 2.1 做什么

- 平台总览看板：覆盖率、成功率、时延、问题趋势、交付健康——管理者视角
- 项目分析看板：单项目审查趋势、问题分布、处置进度、项目内成员活动——项目负责人视角
- 成员分析看板：本人自查 + 管理者团队聚合——自查与辅导视角
- 指标字典：全部指标口径显式化、页面可查（企业级看板的信任基础）

### 2.2 不做什么（红线与取舍）

| 诉求 | 结论 | 对抗理由 |
|---|---|---|
| 成员提交次数/趋势/问题数量 | **授权管理者可见**（2026-08-10 产品决策） | 团队管理与辅导的必需数据。护栏三道：① 仅部门负责人/业务系统负责人/管理员可见成员明细，普通成员仅本人视图；② 查看与导出成员数据全部审计留痕；③ 周/月报告保持团队聚合口径，个人数据不进传播物。不作为绩效评价直接输入 |
| 通用 BI / 拖拽报表 | **不做** | 固定指标字典 + 固定图表；自定义报表是无底洞，报告中心用模板化快照满足汇报需求 |
| 历史提交全量回填 | **首期不做** | ACR 无提交事实存量；首期从 push 载荷增量抽取（见 §3.3），历史回填为演进项（需 API 配额与权限评估） |
| Token/成本分析 | **首期不做** | 任务表无 token 事实（LLM 路径未统计）；先补用量记录再谈成本看板，字段在聚合层预留 |
| 实时看板 | **不做** | 准实时（分钟级延迟）足够；实时流式是成本陷阱 |

### 2.3 与既有页面的分工

- 工作台（M7）：今日待办与最近动态，**不重复建图表**，保留跳转看板的入口
- 审查中心各列表：执行与处置操作界面，看板只读、不下钻到操作
- 看板数据全部来自聚合层，不直查明细表（性能与口径一致性的双重保证）

## 3. 数据基础设计

### 3.1 现状资产

事实层已齐备：`review_webhook_event`（事件）、`review_task`（任务/结论/时长）、`review_issue`（问题/状态/时间）、`review_issue_action`（处置动作/操作人）、`review_delivery_record`（交付）。缺两块：**提交事实**与**聚合层**。

### 3.2 聚合层：review_stats_daily（核心新表）

按「项目 × 日」预聚合，看板查询唯一数据源：

| 列组 | 字段 | 说明 |
|---|---|---|
| 维度 | project_id, stat_date | 联合唯一键 |
| 任务 | task_total, task_success, task_failed, task_push, duration_p95_ms | 覆盖率/成功率/时延的分子分母 |
| 问题 | issue_new, issue_critical, issue_high, issue_medium, issue_low, issue_closed, issue_confirmed, issue_false_positive | 趋势与处置进度 |
| 交付 | delivery_total, delivery_success | 交付健康 |
| 审查事件 | event_accepted, event_ignored | 覆盖率分母（应审口径）与噪声观测 |

**刷新机制**：Quartz 夜间任务全量重算近 35 天（幂等 UPSERT，覆盖式，无增量一致性问题）+ 任务 SUCCESS/FAILED 时异步刷新当日行。重算窗口 35 天保证跨月趋势可查；更早数据冻结不再变（审查事实本身不再变化）。

### 3.3 提交事实：review_commit_fact（成员/项目提交趋势的数据源）

**来源**：push 事件受理时从载荷 `commits` 数组抽取（作者名/邮箱、时间戳、提交消息、SHA）——零新增外部调用，随 M10 push 链路天然落地。PR 事件不产生提交事实（PR 的提交在合并 push 时自然进入）。

| 列 | 说明 |
|---|---|
| project_id, commit_sha, commit_time | 事实主体（project+sha 唯一） |
| author_name, author_email | 成员识别键（邮箱优先，名称兜底） |
| commit_message_first_line | 展示用 |
| source_task_id | 追溯抽取它的审查任务 |

**成员身份口径**（企业级关键点）：ACR 不维护人员主数据（非目标），提交作者按 `author_email` 归一为「提交身份」；与平台用户账号的映射**不强制**——成员看板按提交身份聚合即可，避免绑定企业目录的复杂度。后续接入身份源是演进项。

**聚合**：`review_member_stats_daily`（project_id × author_key × stat_date：commit_count、tasks_reviewed（本人作为 PR 发起人/推送人的被审任务数）、issues_new（本人关联任务新增问题数）、issues_open（未关闭数）），一张表同时支撑两条趋势线与成员明细表——项目提交趋势 = 按 project 汇总，成员提交趋势 = 按 author_key 汇总，成员问题数 = issues 字段。问题与作者的关联经任务的 pr_author/pusher 建立（事实层已有，无需新采集）。

**已知局限（明示）**：① 只有接入后且启用 push 审查的项目有数据；② 合并提交（merge commit）计入，squash 合并的原始提交数丢失——趋势看口径一致性，不看绝对值；③ 历史数据空缺，页面显示「数据自 YYYY-MM-DD 起积累」。

### 3.4 不新增的

不建明细快照表、不建物化视图、不动既有事实表结构（提交事实表是唯一新表 + 两张聚合表）。

## 4. 菜单与信息架构

新增一级菜单**「数据洞察」**（路线图 §4.2 既定名称），四个二级菜单：

| 二级菜单 | 定位 | 阶段 |
|---|---|---|
| 总览看板 | 平台治理健康度，管理者首屏 | 一期 |
| 项目分析 | 项目列表（指标概览）→ 单项目详情（趋势下钻） | 一期 |
| 成员分析 | 本人自查 + 授权团队聚合 | 二期（依赖提交事实积累） |
| 报告中心 | 周/月快照、导出、发送记录 | 三期占位（菜单先挂「即将上线」态） |

菜单顺序遵循路线图「常用业务在前」：数据洞察位于「审查中心」之后、「项目接入」之前。

## 5. 各看板页面设计

### 5.1 总览看板

- **筛选区**：时间范围（近 7/30 天/自定义）、业务系统
- **KPI 卡片行**（4 张）：有效审查覆盖率、审查成功率、P95 时延、未处置重点问题数（CRITICAL+HIGH 且未关闭）——每张卡带环比箭头与口径 tooltip
- **趋势区**：审查任务趋势（成功/失败堆叠柱）、新增问题趋势（严重度堆叠）
- **分布区**：问题类别分布（横向条形）、交付渠道健康（成功率表）
- **指标口径入口**：页面右上角「指标说明」抽屉，展示指标字典（§6）——企业级信任设计，每个数字可解释

### 5.2 项目分析

- **列表页**：项目 × 近期指标矩阵（任务数、成功率、新增问题、未关闭重点、处置率、最近审查时间），列可排序——**仅排序，不做名次渲染**（不显示「第 N 名」、不标红倒数）
- **详情页**（点击项目进入）：
  - 头部：项目/业务系统/负责人/时间范围筛选
  - 趋势：审查任务趋势、问题趋势、**项目提交趋势**（来自 commit 聚合）
  - 构成：问题严重度/类别分布、处置漏斗（新增→确认→关闭）
  - 项目内成员活动表：提交身份 × 提交数 × 被审变更数 × 关联问题数（**仅本项目内聚合，无跨项目对比**）
- 空态：无数据项目显示接入引导文案

### 5.3 成员分析（管理可见 + 三道护栏）

- **默认视图 = 本人**：当前用户关联的提交身份（邮箱匹配平台账号邮箱，匹配不到则按账号名模糊候选 + 手动认领）自查：我的提交趋势、我的变更被审查情况、我相关的未关闭问题
- **团队视图（授权管理者）**：部门负责人/业务系统负责人/管理员可见所辖范围：
  - 成员提交趋势叠加图（可开关单个成员曲线）
  - **成员明细表**：提交身份 × 提交次数 × 提交趋势 × 被审变更数 × 关联问题数 × 未关闭问题数，列可排序——服务于团队管理与辅导
  - 团队问题处置进度
- **护栏（产品决策 2026-08-10）**：
  1. 权限收口：成员明细仅授权管理者可见，普通成员仅本人视图；
  2. 审计留痕：查看成员明细、导出成员数据全部记操作日志（复用 oper_log）；
  3. 不进传播物：周/月报告保持团队聚合口径，不含个人名次；个人数据仅系统内可查；
  4. 定位声明：页面标注「用于团队管理与辅导，不作为绩效评价直接输入」。
- **配套动作**：路线图 §1.3/§2.2 红线条款同步修订为本决策口径（避免原文与新形态冲突）。

### 5.4 报告中心（三期占位）

一期菜单挂「即将上线」；设计预留：周/月模板快照（聚合层数据直接冻结）、导出（异步任务 + 站内信提醒，企业习惯）、发送记录。不做拖拽设计器。

## 6. 指标字典（一期口径，基于已验证数据）

| 指标 | 口径 | 基线参考（联调数据） |
|---|---|---|
| 有效审查覆盖率 | SUCCESS 且投递 SUCCESS 的任务 / ACCEPTED 事件对应任务 | 17/24 |
| 审查成功率 | SUCCESS / 全部终态任务 | 70.8%（联调期含开发失败，生产预期 >95%） |
| P95 审查时延 | 成功任务 duration_ms 95 分位 | 样本不足，max 215s 记基线 |
| 新增问题数 | origin=NEW 物化数，按日/严重度 | 54/6 天 |
| 处置率 | (确认+关闭) / 全部问题 | 8/54——**试点期核心改进目标** |
| 平均关闭时长 | CLOSED 问题创建→关闭时间均值 | 待积累 |
| 误报率 | FALSE_POSITIVE 关闭 / 全部关闭 | 样本不足，先展示不考核 |
| 交付成功率 | 投递 SUCCESS / 全部投递尝试 | 100%（17/17） |
| 复核流转率 | 进入 RECHECKING 的问题占比 | 48%——churn 观测指标，验证 M10.2 修正效果 |
| 提交活跃度 | commit_fact 按日/项目/身份计数 | 自数据积累起 |

口径变更必须版本号化（指标字典入 sys_config 或独立文档），看板页脚展示口径版本——避免「同一个数昨天今天不一样」的企业信任事故。

## 7. 权限设计

| 看板 | 权限 | 数据范围 |
|---|---|---|
| 总览 | `insight:overview:view`（新权限串） | 按用户业务系统/部门数据范围聚合 |
| 项目分析 | `insight:project:view` | 复用项目 DataScope（部门+负责人） |
| 成员分析-本人 | 登录即有 | 仅本人认领的提交身份 |
| 成员分析-团队 | `insight:team:view` | 部门负责人看本部门、业务系统负责人看本系统、管理员全量 |

数据范围全部走既有 DataScope 机制扩展，不新建权限体系。

## 8. 交互规范（大陆企业后台习惯）

- 列表页「时间范围 + 业务系统 + 项目」三段筛选 + 高级筛选收起；筛选状态持久化（最近筛选记忆）
- KPI 卡片环比用「较上期 ↑/↓ 百分比」，不用红绿涨跌色暗示好坏（质量数据不是股价）
- 全部图表可导出 PNG（ECharts 原生）；表格导出 Excel 走异步任务
- 空态三件套：无数据原因 + 积累起始日期 + 接入/配置引导链接
- 看板加载用骨架屏，失败给「重试」不给白屏
- 移动端：KPI 卡片响应式降为单列，趋势图横向滚动（负责人移动端看数是真实场景）

## 9. 分阶段交付

| 阶段 | 内容 | 依赖 |
|---|---|---|
| 一期 | review_stats_daily + 夜间聚合任务 + 总览看板 + 项目分析（不含提交趋势）+ 指标字典 | 架构批次合入后开工 |
| 二期 | review_commit_fact + push 受理抽取 + commit 聚合 + 项目提交趋势 + 成员分析 | 一期聚合层稳定 |
| 三期 | 报告中心（模板快照/导出/发送记录）+ token 用量记录与成本视图 | 二期数据积累 ≥1 个月 |

## 10. 验收标准（一期）

1. 总览/项目看板数字与明细表人工核对一致（抽样 3 项目 × 3 指标）；
2. 聚合重算幂等：重复执行结果不变；任务完成后当日数据 1 分钟内更新；
3. 权限：跨部门用户看不到非授权项目数据（抽查）；
4. 指标字典页覆盖全部展示指标；
5. 空态/无数据项目展示引导而非 0 值误导。

## 11. 风险

| 风险 | 等级 | 应对 |
|---|---|---|
| 成员数据被挪作绩效评价引发争议 | 中 | 三道护栏落地（权限收口 + 审计留痕 + 不进传播物）+ 页面定位声明 + 路线图口径同步修订；导出成员数据强制审计 |
| 提交数据缺口（仅增量、无历史）被误读 | 中 | 页面明示积累起始日期；趋势图不 extrapolate |
| 聚合与明细不一致 | 中 | 覆盖式重算（非增量累加）；验收含人工对账 |
| 看板性能 | 低 | 聚合表 + (project_id, stat_date) 唯一索引；明细表零直查 |
| 与架构批次冲突 | 中 | 一期开发待架构批次合入后开工；Quartz 任务注册与调度层改动需协同 |
