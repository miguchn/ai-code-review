# 企业级产品与端到端体验 Review（2026-08-23）

## 1. 结论

平台已经具备 V0.2 受控推广所需的核心闭环：项目接入、Webhook 受理、审查任务、审查记录、问题台账、投递、工作台、数据洞察，以及 RBAC × 部门范围 × 项目成员的权限边界。使用本地存量 MySQL 数据完成端到端浏览后，核心页面可用、数据关联基本完整、敏感凭据默认不回显。

平台仍不满足中国企业内部正式规模化使用的 V1.0 准入。当前最需要补齐的不是更多页面，而是部署依赖就绪检查、企业身份与账号生命周期、完整业务审计、数据留存与恢复、规则/模型发布治理、非 GitHub Provider 真实验收，以及可追溯的数据下钻与报告能力。

本次已直接修复三个定位明确且风险可控的问题：

1. Docker 后端只能连接 Compose 内置 MySQL，无法复用宿主机存量测试库；
2. Webhook 在验签前占用 `deliveryId` 去重键，伪造请求可抢占合法投递 ID；
3. 模型连接测试成功时向页面返回供应商原始响应摘要，可能暴露 `reasoning_content`。

## 2. Review 范围与证据

### 2.1 实际环境

- Docker Compose：`backend`、`frontend`、`mysql`、`redis` 四个服务均为 healthy；
- 后端实际连接宿主机 `ai_code_review` 存量库，而不是新建业务数据；
- 存量事实：2 个项目、1 个任务、3 个问题、1 次运行、1 条投递、1 个模型配置；
- 仅执行缺失的 `sql/49_issue_auto_assignment.sql` 增量迁移；未执行会重建数据的 `init-full.sql`；
- 未新增项目、任务、问题、用户或通知渠道。登录与模型连接测试会按既有逻辑更新运行日志或健康检测时间。

### 2.2 实际浏览页面

- 工作台：今日待办、最近动态、快捷入口、任务状态、模型状态、审查结论；
- 审查中心：任务列表/详情、审查记录/详情、问题台账/详情、投递记录/正文；
- 项目接入：业务系统、代码项目、项目成员、Git 凭据、项目六类配置页签；
- 策略配置：审查模板、大模型配置、审查引擎；
- 通知管理：通知渠道、投递记录；
- 数据洞察：总览、项目、成员、Token 用量、指标说明；
- 系统治理：用户、角色、业务审计、运行概览。

### 2.3 后台逻辑核查

- 项目访问按功能权限、组织数据范围和项目成员角色取交集，按 ID 的详情与动作也做项目校验；
- 凭据、模型、模板、通知渠道和引擎要求平台级角色权限，部门角色不能只靠同名权限串越权；
- 问题状态变化采用原子更新，并写问题动作和业务审计前后快照；
- Git 凭据、Webhook Secret、通知 Webhook 和模型 API Key 均不在查询/编辑页面回显明文；
- Webhook 的验签、去重、事件落库和任务创建顺序已修正并由单元测试约束。

## 3. 重点问题

| 优先级 | 问题 | 影响 | 状态/建议 |
|---|---|---|---|
| P0 | Docker 数据源写死为 Compose `mysql`，存量卷缺少最新字段时后端健康检查失败，前端被依赖关系阻断 | 直接违背一键启动预期，无法使用宿主机已有测试数据 | **已修复**：数据源参数化、增加 `host.docker.internal` 映射并补充存量库说明；当前四服务 healthy |
| P0 | Webhook 先落去重记录、后验签 | 攻击者可用伪造请求抢占合法 `deliveryId`，导致真实事件被当成重复投递 | **已修复**：先匹配项目并验签，成功后才占用去重键；非法/超限请求不写去重表 |
| P1 | 模型连接测试成功结果回显原始响应摘要 | 供应商扩展字段可能含推理内容或其他不应展示的信息 | **已修复**：成功结果只返回解析后的最小内容和用量；页面仅在失败时显示脱敏错误摘要，并提示测试会产生少量 Token |
| P1 | Docker 后端镜像没有 OCR CLI，但存量项目启用了 OCR | 平台能启动，新的 OCR 审查任务会执行失败 | **可见性已补齐**：项目配置和运行概览展示探针状态；仅在存在启用 OCR 项目时告警；任务失败给出安装/配置指引。CLI 仍保持可选，不进入默认镜像 |
| P1 | 存量数据库没有迁移版本事实和自动升级机制 | 新装可用 `init-full.sql`，旧卷/共享库只能靠人工判断“尚未执行”的脚本，容易漏升级或重复执行 | 短期增加启动前 schema preflight 和明确缺失版本；中期引入受控版本表/迁移工具，禁止对存量库自动执行破坏性初始化 |
| P1 | 业务审计覆盖不完整且不可导出 | 问题、项目、角色等有业务审计，但 Git 凭据、通知渠道等敏感配置主要依赖通用操作日志；无法形成完整审计证明 | 建立敏感对象覆盖清单，补齐 before/after、原因、关联对象和失败操作；支持日期、对象、操作者筛选及受控导出 |
| P1 | 企业身份和账号生命周期缺失 | 无 SAML/OIDC/LDAP/SCIM，入转调离、到期、自动回收和定期访问复核无法闭环 | 作为 V1.0 准入项；优先 OIDC/SAML + 账号停用/权限回收联动，不先建设通用 IAM |
| P1 | 通知链接依赖 `ACR_PUBLIC_BASE_URL`，未配置时可发送 `localhost` | 企业微信群收到的审查链接对其他用户不可访问 | 启动/项目连接检查中校验公网或内网可达基础 URL；存在启用渠道时将 localhost 设为阻断性配置告警 |
| P1 | GitLab/Gitee/Gitea 只有适配器、契约测试和自动测试证据 | 页面看似支持四平台，但无法宣称企业生产可用 | 路线图和页面标识为“待真实环境验收”，逐个平台完成 Webhook、拉取、回写、重试与权限失败演练 |
| P1 | 三个真实问题已待确认约 12 天且无人负责 | 有问题台账但闭环运营不足；M13 不回填历史问题，存量问题仍未指派 | 提供安全的存量问题批量指派/重算入口，增加项目级 SLA、逾期升级和负责人看板；不自动改变现有处置状态 |
| P2 | 洞察指标与任务/问题证据之间缺少下钻，主要只能导出图表 PNG | 管理者看到异常后仍需手工切换列表和重建筛选；无法形成可复核的数据包 | KPI、项目行、成员行跳转到带同口径筛选的明细；先补 CSV/Excel 导出，再建设不可变报告和订阅 |
| P2 | Token 成本缺少币种、价格版本、预算与配额 | `0.00` 容易被误读，历史成本会随当前单价变化，无法做部门/项目治理 | 明示币种和“估算”；保存任务运行时的价格版本/成本快照；后续增加提醒型预算，再评估强制限额 |
| P2 | 模板和模型缺少发布、审批、版本历史与回滚 | 内置模板只读和复制能避免误改，但企业规则变更无法审计发布、灰度和快速回退 | 在现有模板版本字段上补“草稿—发布—停用”与不可变版本；高风险变更可选双人复核，不建设通用流程引擎 |
| P2 | 角色列表部分图标按钮缺少可访问名称 | 键盘和辅助技术用户难以识别操作，也降低自动化回归稳定性 | 为图标按钮补 `aria-label`/tooltip，纳入前端可访问性扫描 |

## 5. 路线图调整建议

### R0：先形成“可部署、可运行、可发现故障”的发布门槛

1. 存量库 schema preflight、迁移版本事实和失败指引；
2. OCR/LLM/Git Provider/通知 URL 的启动与周期性依赖检查；
3. 运行概览纳入引擎不可用、模型连续失败、公共 URL 无效和迁移缺失告警；
4. 保留质量门禁为 shadow，不在问题误报率和处置闭环未稳定前直接阻断研发流水线。

### R1：完成 V1.0 企业治理准入

1. OIDC/SAML 或完整账号生命周期至少完成一条可验收路径；
2. 敏感对象业务审计覆盖、查询、受控导出和留存策略；
3. 数据库/文件备份、恢复演练、RPO/RTO 与删除证明；
4. 项目问题 SLA、逾期升级、存量指派和责任人运营看板。

### R2：扩大真实接入面和策略治理能力

1. 按目标客户优先级完成 GitLab/Gitee/Gitea 真实环境闭环，不按 Provider 数量做虚假完成度；
2. 模板/规则/模型的不可变版本、发布、回滚和可选审批；
3. Token 价格版本、成本快照、项目/部门配额提醒。

### R3：完善证据传播与门禁

1. 洞察到任务/问题/投递的同口径下钻与 CSV/Excel 导出；
2. 不可变周/月报告、权限隔离、订阅和发送记录完成后再开放报告中心；
3. shadow 数据证明命中率、误报率和人工豁免机制后，再逐项目启用质量门禁。

- 浏览过程中未发现前端控制台错误；未通过真实 Webhook 创建任务，以避免污染用户的存量测试数据。
