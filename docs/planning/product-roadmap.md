# AI Code Review 产品路线图

## 1. 产品结论

### 1.1 定位

AI Code Review 面向企业内部研发团队，是部署在代码托管平台旁侧的**代码审查治理平台**。它负责把代码事件转化为可追踪的审查、整改、度量和审计闭环；GitLab、GitHub、Gitee、Gitea 等代码平台仍是代码协作与合并事实源。

产品主链路为：

> 项目接入 → 事件可信接收 → 审查执行 → 结论回写 → 问题整改 → 复核关闭 → 质量度量与审计。

北极星指标是**有效审查覆盖率**：在约定时限内完成审查并成功向代码平台交付结论的应审 MR/PR 数，占全部应审 MR/PR 数的比例。它必须与审查成功率、P95 审查时延、有效问题率、问题按期关闭率和误报率一起观察，不能用“生成了多少条问题”衡量产品价值。

### 1.2 目标用户

| 角色 | 核心任务 | 默认关注范围 |
|---|---|---|
| 开发者 | 查看本人变更的审查结论，修复、申诉或标记误报 | 本人及被授权项目 |
| 项目负责人 | 接入仓库、选择审查方案、处理阻断和逾期问题 | 所负责业务系统与项目 |
| 质量/安全负责人 | 维护规则、复核高风险问题、观察质量趋势 | 被授权组织与业务系统 |
| 研发管理者 | 查看覆盖、质量、整改和成本趋势，推动跨项目治理 | 授权组织的汇总数据，默认不查看代码正文 |
| 平台运维管理员 | 管理连接、模型、容量、失败恢复和运行告警 | 平台运行域，不默认查看代码正文 |
| 审计人员 | 只读查询权限、配置变更、审查决策和外部交付证据 | 明确授权的审计范围 |

### 1.3 明确非目标

- 不替代 Git 平台、代码搜索平台、IDE 或人工审批；
- 不建设通用项目管理、工单、工作流或聊天机器人平台；“任务”只表示一次审查执行，“问题”只跟踪审查发现；
- 不建设通用 BI 或 APM；数据看板只解释代码质量，系统监控只保障本平台；
- 首期按单企业内部部署设计，不预建 SaaS 多租户、商业计费和跨企业数据运营；
- 不以个人排行榜、提交次数或问题数量做绩效评价；个人视图用于自查和经授权的辅导；
- 不在未经审批的情况下用误报数据自动修改生产规则或 Prompt；
- 不承诺首版同时支持全部 Git 平台、通知渠道、Push 审查、全量扫描和强制合并卡点。

### 1.4 企业内部商用准入

功能跑通不等于可商用。进入内部正式使用前必须同时满足：

1. **闭环**：至少一个真实 Git 平台、一个审查执行路径和一个通知渠道完成接入、审查、回写、整改、复核；
2. **安全**：凭据加密、响应和日志脱敏，代码/Diff/Prompt/模型响应的外发与保留策略明确；
3. **权限**：组织、业务系统、项目和操作权限能组合授权，跨项目不可见；
4. **可靠性**：事件幂等、步骤重试、外部副作用防重、超时限流、失败恢复和降级原则明确；
5. **可运营**：任务成功率与时延可观测，异常可告警，备份恢复、容量和数据清理有操作说明；
6. **可审计**：关键配置、权限、审查结论、人工处置、回写和通知均可追溯。

- 现有通用 RBAC、部门数据范围和操作日志已用于项目接入，但尚不能证明后续审查问题的完整项目级隔离、审查决策审计或审查链路可观测。

### 2.2 原规划的核心问题与处置

| 级别 | 对抗性问题 | 直接风险 | 本次结论 |
|---|---|---|---|
| 阻断 | P0 同时要求四个 Git 平台、多通知渠道、inline 回写、自动降级和完整编排 | 横向适配很多，真实闭环迟迟不可用 | 首个版本只做一个平台、MR/PR 事件、一个渠道和一种回写，再按契约扩展 |
| 阻断 | 凭据加密、数据保留和细粒度权限被放在后期或仅列为待决策 | 试点即可能泄露代码资产和密钥 | 提升为 P0 准入项，不满足不得接入真实仓库 |
| 高 | “审查任务、审查记录、缺陷、报告、定时任务”没有稳定语义 | 菜单重复、状态混用、指标无法对账 | 固定为执行实例、可整改问题、不可变汇总快照、调度配置四类对象 |
| 高 | 路线图止于回写和通知，“已修复”如何确认未落定 | 无法证明业务闭环 | 加入问题复核；人工确认是首版保底，后续提交重审为演进方向 |
| 高 | 首页工作台、数据看板、报告中心未区分 | 三个页面重复堆图表 | 工作台负责“今天做什么”，看板负责“为什么变化”，报告负责“冻结并传播结论” |
| 高 | 通用 RBAC 被当作完整数据权限 | 有菜单权限的人可能跨项目看到代码与结论 | 增加组织/业务系统/项目范围授权，按钮权限只控制动作 |
| 高 | 通用操作日志被当作业务审计 | 无法还原规则版本、模型版本、人工忽略和合并旁路 | 建立统一审查审计事件，保留操作者、对象、前后值、原因和关联标识 |
| 中 | 通知投递与风险预警混为一体 | 送达失败、质量风险和系统故障无法分责 | 分为业务通知、风险预警、运行告警三类，统一进入可追踪事件中心 |
| 中 | 系统监控只覆盖 CPU、缓存和数据源 | 审查大量失败时基础资源仍可能“全绿” | 增加业务 SLI：积压、成功率、时延、引擎/Provider/通知可用性 |
| 中 | “成员分析”容易演变为个人排名 | 激励刷指标并产生劳动管理风险 | 改为团队/项目聚合；个人只看本人或经授权的辅导视图，不提供排行榜 |
| 中 | Session 回放、项目哨兵、SARIF 等并列进入承诺路线 | 未验证价值却提前固化结构 | 移出近期承诺；满足明确场景和使用量门槛后单独立项 |

### 2.3 本地参考项目能力审计

本次基于本地 PR-Agent（`b249e568`）、AI-Codereview-Gitlab（`f464234`）和 open-code-review CLI（`1.8.1`）进行能力核对。参考项目用于验证行业常见能力，不作为本产品的菜单或代码模板。

| 参考项目 | 已验证的标准能力 | 值得借鉴 | 不直接照搬 |
|---|---|---|---|
| PR-Agent | 多 Git Provider、Webhook/Action/CLI、多模型；`review`、`improve`、`describe`、`ask` 等 PR 工具；增量审查、大变更压缩、动态上下文、自反思、仓库级配置、持久评论 | Provider 能力声明与契约测试；自动触发与人工重跑并存；大变更分片且显示覆盖范围；同一 MR 更新持久总结、减少评论噪声；区分给审查者的风险结论和给作者的可执行建议 | 不把 PR 描述、问答、补文档、改 Changelog 等扩成首版产品；不暴露大量模型参数给普通用户；不照搬斜杠命令作为国内后台主要交互 |
| AI-Codereview-Gitlab | GitLab/GitHub/Gitea Webhook、MR/Push 审查、评论回写、钉钉/企微/飞书、日报、Dashboard、多模型、Diff/Agent 两种审查路径、本地仓库缓存 | 国内 IM 触达和“账号（姓名）”展示；项目模板减少重复配置；Agent 只读沙箱、路径限制、超时和资源提示；审查完成后直接回到 MR/PR 场景 | 不采用娱乐化或讽刺审查风格；不做“摸鱼/甩锅”式个人排行；不能把代码平台 Access Token 当 Webhook Secret；不使用静默自动降级掩盖结论口径变化；不以 `.env + SQLite` 作为企业治理方案 |
| open-code-review | Git diff/分支/提交审查、全文件扫描；确定性文件筛选、关联文件分组、路径规则匹配；Agent 读取/搜索上下文；结构化行级评论、评论反思、Session 恢复、CI/CD、OpenTelemetry | 把文件范围、分组、规则匹配、定位校验交给确定性流程；把 Agent 限定在上下文探索和判断；以准确率、召回率、时延、Token 联合评估效果；保留引擎 Session ID 便于恢复和诊断 | CLI 配置、Session Viewer 和委托模式不是管理平台的主导航；全量扫描与 MR 增量审查分开立项和统计；在误报率未达标前不因引擎具备行级评论就直接强制门禁 |

由此形成四条产品原则：

1. **低噪声优先**：问题数量不是目标，优先提高有效性、定位准确性和建议可执行性；
2. **确定性流程托底**：文件范围、规则匹配、版本快照、幂等和定位校验由工程流程保证，模型只做适合它的判断；
3. **代码平台内完成主要反馈**：平台后台负责治理、追踪和度量，开发者的日常操作尽量回到 MR/PR；
4. **国内企业体验优先**：中文业务命名、列表与筛选优先、角色化待办、钉钉/企微/飞书、组织/业务系统/项目数据范围和可导出审计是主线能力。

## 3. 产品业务架构

### 3.1 能力分层

| 层级 | 业务域 | 核心能力 | 边界 |
|---|---|---|---|
| 用户触点 | 工作台、审查中心、项目接入、数据洞察 | 待办处理、任务查询、问题整改、项目配置、质量分析 | 不承载后台编排规则 |
| 审查闭环 | 事件、任务、问题、交付、报告 | 可信接入、执行、结论、回写通知、整改复核、快照 | 只管理代码审查相关事实 |
| 策略控制 | 审查方案、规则库、模型服务、质量门禁 | 规则/模型选择、阈值、范围、版本、灰度与回滚 | 每次任务必须保存生效版本快照 |
| 平台治理 | 组织权限、业务系统、凭据、审计、数据生命周期 | 资产隔离、安全、合规和责任追踪 | 不接管代码平台本身的用户与仓库管理 |
| 运行保障 | 运行监控、异常恢复、调度、容量与告警 | SLI、重试、熔断、配额、备份恢复 | 不发展为通用 APM 或作业平台 |
| 外部集成 | Git Provider、OCR/LLM、通知渠道、身份源 | 屏蔽平台差异、验证连接、记录外部副作用 | 外部失败不得污染内部审查事实 |

### 3.2 核心对象与唯一职责

| 对象 | 业务含义 | 关键关系 | 不应承载 |
|---|---|---|---|
| 业务系统 | 企业内部产品/系统归属与责任边界 | 关联部门、负责人和多个代码项目 | Git 凭据、审查执行状态 |
| 代码项目 | 一个接入的 Git 仓库及其审查范围 | 归属业务系统，绑定连接和审查方案 | 模型密钥正文、通用组织信息 |
| 审查方案 | 某范围内生效的规则、模型、阈值、通知与门禁组合 | 可绑定项目/分支，发布后有版本 | 审查结果和运行日志 |
| 审查任务 | 一次由事件、人工或调度触发的执行实例 | 关联事件、项目、变更版本和策略快照 | 跨任务的问题整改状态 |
| 审查问题 | 可被定位、指派、复核的单个发现 | 首次发现于任务，可在后续任务中复核 | 整份模型原始输出 |
| 交付记录 | 一次评论、状态检查或通知副作用 | 关联任务/问题，拥有独立幂等键和状态 | 改写审查结论 |
| 报告快照 | 某时间范围和口径下不可变的汇总结果 | 可钻取到任务和问题 | 实时待办、可编辑问题状态 |
| 审计事件 | 权限、配置、决策和人工操作的追踪证据 | 关联操作者、对象、前后值与原因 | 大体量 Diff 或模型响应正文 |

审查任务状态只表达执行：`待执行 → 执行中 → 已完成 / 已失败 / 已取消`；审查结论独立表达 `通过 / 警告 / 阻断`；回写和通知各自保存投递状态。禁止用一个“成功/失败”字段同时表达审查、回写和通知结果。

审查问题状态建议收敛为：`待确认 → 待修复 → 待复核 → 已关闭`，`已忽略`和`误报`作为有原因、有权限、有审计的终态。首版允许人工复核，后续再增加基于新提交的自动重审，不以字符串或行号简单匹配自动关闭。

### 3.3 端到端流程

1. **接入**：管理员创建代码项目，验证连接，绑定业务系统、数据范围和已发布审查方案；
2. **接收**：Webhook 先完成项目识别、载荷限制、验签、重放防护和事件去重，再快速响应；
3. **建单**：按事件唯一键创建审查任务，记录触发来源、提交基线和关联标识；
4. **准备**：拉取允许范围内的 Diff/必要上下文，检查大小、语言、分支和排除规则；
5. **执行**：冻结规则、Prompt、模型和阈值版本，调用受控审查引擎并标准化结果；
6. **判定**：保存问题，计算通过/警告/阻断结论；模型建议与平台门禁决策分离；
7. **交付**：以独立幂等键回写评论/状态并发送通知；局部投递失败不回滚已完成的审查；
8. **整改**：责任人确认、修复、忽略或申诉，所有人工动作记录原因；
9. **复核**：人工确认或后续重审关闭问题，保留首次发现与关闭证据；
10. **度量**：任务和问题事实进入看板，周期性冻结为报告快照，并可回查原始记录。

失败按步骤分类为可重试、需人工处理和不可重试。重试必须从安全步骤开始；对评论、状态检查和通知等外部副作用必须先查投递记录，不能因整任务重跑而重复发布。

## 4. 目标菜单与信息架构

### 4.1 设计原则

目标结构控制为八个中文一级入口，常用业务在前、治理运维在后，默认不超过两级。动态菜单按角色和数据范围显示；本路线图定义逻辑归属，不要求一次性重做现有后台菜单。

- 开发者主要在代码平台和工作台处理待办，后台不复制 Git 平台的 MR/PR 页面；
- 项目负责人采用“代码项目 → 审查方案 → 接入校验 → 试运行 → 启用”向导式流程；
- 质量和管理角色采用“看板发现异常 → 下钻任务/问题 → 处理或调整方案”的分析路径；
- 平台管理员采用“运行概览 → 异常列表 → 任务/投递详情 → 重试或处置”的运维路径；
- 菜单名使用企业用户熟悉的“工作台、台账、方案、审计、预警、运维”，避免直接暴露 Adapter、Provider、Prompt、Session 等技术名词。

### 4.2 一级菜单、子菜单与页面核心功能

| 一级菜单 | 子菜单/页面 | 页面核心功能 | 首次交付 |
|---|---|---|---|
| 工作台 | 无固定子菜单 | 范围切换、我的待办、阻断/逾期/失败提醒、今日摘要、最近动态、快捷操作 | MVP |
| 审查中心 | 审查任务、审查记录、问题台账 | 任务作执行队列（待执行/执行中/失败重试）；记录展示已完成结果与评分；问题确认、指派、修复、申诉、误报、复核与历史 | MVP / 核心版 |
| 项目接入 | 代码项目、连接管理 | 代码平台连接、凭据引用、连通性；仓库归属、负责人、分支/路径/事件范围、Webhook 校验、试运行和启停 | MVP |
| 策略配置 | 审查方案、规则库、模型服务 | 方案草稿/校验/发布/回滚；规则分类、路径匹配和版本；模型端点、密钥、连接测试、用量限制与可用状态 | MVP 基础 / 核心版完整 |
| 数据洞察 | 质量看板、报告中心、成本与配额 | 指标筛选、对比和下钻；周/月报告生成、版本、导出、订阅、发送记录；Token/调用量、预算和限额 | 企业版 / 规模化版 |
| 通知预警 | 通知策略、投递记录、预警事件、渠道与模板 | 事件/严重度/收件范围、聚合频控；消息内容预览、测试发送、失败重试；质量风险和运行异常确认/关闭 | 核心版 / 企业版 |
| 系统治理 | 组织与用户、角色与权限、业务系统、审查审计、基础配置 | 账号和组织、功能与数据授权、系统归属；权限/配置/处置/旁路/导出审计；复用字典、参数和公告 | 现有基础 / MVP增强 |
| 运维中心 | 运行概览、调度任务、服务资源、在线会话 | 积压、成功率、P95 时延、依赖健康、异常入口；Quartz 调度；服务器、Redis、Druid 和在线用户 | 现有基础 / MVP增强 |

菜单去重规则：

- “审查任务”与“审查记录”职责分离：任务=执行队列，记录=已完成历史结果（M3.1）；不另建结果业务表，复用 `review_task` / `review_task_run`；
- “缺陷流转”统一命名为“问题台账”，不建设通用缺陷管理；
- Quartz“调度任务”与“审查任务”必须分属运维中心和审查中心；
- 报告中心只保存周期快照、导出和订阅，不复制任务列表或实时看板；
- 模型服务管理连接和密钥，审查方案决定项目实际使用哪个模型及降级顺序；
- 业务通知、风险预警、运行告警共用事件与投递能力，但触发规则和权限分开。

### 4.3 国内企业后台交互约定

- 列表页采用“顶部常用筛选 + 高级筛选 + 表格 + 分页”，默认保存最近筛选，状态、负责人、业务系统和项目均可筛；
- 详情优先使用独立详情页或右侧抽屉展示概览、问题、步骤、交付和审计时间线，不在多层弹窗中完成长流程；
- 新建项目和发布方案使用分步表单，提交前给出配置校验与影响范围；试运行成功后才能启用真实 Webhook；
- 忽略高风险、发布方案、停用项目、重试外部投递、导出敏感数据等操作二次确认，并要求填写原因；
- 批量操作只开放低风险场景；报告和大批量导出使用异步任务，完成后通过站内消息提醒下载；
- 同一页面同时展示中文状态名称、更新时间和责任人；技术错误码进入详情，列表只显示可执行的中文处置建议；
- 钉钉、企业微信、飞书账号映射显示“账号（姓名）”，但外部昵称不作为权限和人员主数据源。

## 5. 首页工作台、看板与报告

### 5.1 首页工作台：行动优先

首页回答“我今天需要处理什么”，默认不堆叠长期趋势图。

| 区域 | 内容 | 角色化差异 |
|---|---|---|
| 范围与健康 | 当前组织/业务系统/项目范围、接入状态、最近数据时间 | 普通用户只显示有权限范围 |
| 待办卡片 | 待确认问题、待复核问题、阻断变更、失败任务、投递失败、逾期项 | 按角色显示可执行项，不显示无权明细 |
| 今日摘要 | 应审/已审、审查成功率、P95 时延、新增高风险、关闭问题 | 管理者看团队，开发者看本人 |
| 最近动态 | 最近任务、问题状态变化、策略发布、重要告警 | 审计人员可跳转证据链 |
| 快捷操作 | 接入项目、重试任务、处理问题、发布方案、查看告警 | 根据按钮权限显示 |

### 5.2 数据看板：解释变化

质量看板面向项目负责人和质量/安全负责人，至少支持时间、组织、业务系统、项目、分支、语言、严重度和规则维度筛选，并可从图表钻取到任务和问题。

首批指标统一定义：

- 有效审查覆盖率、任务成功率、P50/P95 审查时延；
- 通过/警告/阻断分布，高风险问题新增与存量；
- 问题确认率、关闭率、按期关闭率、平均/中位关闭时长；
- 误报率及其规则分布；
- 每千行受审变更的问题密度（仅在 Diff 行数口径可靠后启用）；
- Token/调用量/估算成本（只有定价版本和币种口径明确后展示金额）。

看板必须展示口径说明、数据截止时间和权限范围。禁止以未经上下文校正的个人问题数、提交数或“代码质量分”做排行榜。

### 5.3 报告中心：冻结与传播

报告是指定周期、范围、指标口径和策略版本下的不可变快照。V1.0 先提供周报/月报模板、手动生成、导出、订阅和发送记录；不建设拖拽式报表设计器。报告中每个异常数字应能回查任务或问题，重新生成产生新版本，不覆盖已发送版本。

## 6. 重点能力审计与优先级

优先级映射为：MVP 是真实试点准入，核心版补齐整改和策略治理，企业版达到内部商用标准，规模化版再扩平台和强治理。

| 功能 | 解决的问题 | 主要角色 | 核心流程 | 建设阶段 |
|---|---|---|---|---|
| 首页工作台 | 用户登录后不知道先处理什么，管理者也无法快速判断风险 | 全部角色 | 识别角色与数据范围 → 汇总待办/风险/失败 → 跳转任务、问题或告警处置 | MVP 基础；核心版角色化 |
| 代码项目与连接 | 仓库、业务系统、负责人、凭据和审查范围分散，接入不可控 | 项目负责人、平台管理员 | 新建连接 → 加密凭据与连通性测试 → 新建代码项目 → 绑定归属/方案 → 试运行 → 启用 | MVP |
| Webhook 事件接入 | 伪造、重复、超大或无关事件会造成安全风险和重复成本 | 平台管理员、项目负责人 | 项目识别 → 载荷限制 → 验签/防重放 → 标准化/去重 → 持久化 → 快速响应 | MVP |

| 审查任务 | 一次审查的进度、失败步骤、结果和重试散落，无法运营 | 开发者、项目负责人、平台管理员 | 事件建单 → 分步执行 → 展示进度/结论/交付 → 失败分类 → 从安全步骤重试或取消 | MVP |

| 问题台账 | 审查意见发出后无人负责，修复、忽略和误报没有证据 | 开发者、项目负责人、质量负责人 | 问题确认 → 指派/认领 → 修复或申诉 → 人工/重审复核 → 关闭；忽略/误报留原因 | MVP 基础确认/关闭；核心版完整流转 |
| 审查方案与规则库 | 全局 Prompt 难适配不同项目，配置变化影响历史结果 | 项目负责人、质量/安全负责人 | 维护规则 → 按路径/语言匹配 → 组合模型/阈值/通知 → 校验 → 发布版本 → 项目绑定 → 回滚 | MVP 固定基础方案；核心版版本治理 |
| AI 模型服务 | 密钥、端点、模型选择、限额和降级缺少企业治理 | 平台管理员、质量负责人 | 新增服务 → 加密密钥 → 连通性测试 → 配置可用模型/限额 → 方案引用 → 记录实际模型与用量 | MVP 安全接入；核心版模型策略；企业版成本 |

| 质量看板 | 管理者看不到覆盖、有效性、整改和趋势，也无法回查依据 | 项目负责人、质量/安全负责人、管理者 | 选择范围/时间 → 查看统一指标 → 对比趋势/分布 → 下钻到项目、任务和问题 | 企业版 |
| 报告中心 | 周/月汇报依赖人工拼表，发送后口径和证据不可复现 | 项目负责人、质量负责人、管理者 | 选择模板/范围/周期 → 生成不可变快照 → 审阅 → 导出/订阅/发送 → 回查任务与问题 | 企业版 |

| 系统监控 | CPU 正常不代表审查正常，积压、超时和外部依赖故障可能无人发现 | 平台管理员、值守人员 | 采集任务/步骤/依赖 SLI → 阈值判定 → 告警 → 下钻异常 → 重试/限流/熔断 → 关闭复盘 | MVP 关键 SLI；企业版完整运维 |
| 成本与配额 | 模型调用成本无法归属，单项目可能耗尽企业预算 | 平台管理员、项目负责人、财务/管理者 | 记录任务用量 → 按项目/模型/时间聚合 → 绑定定价版本 → 预算提醒 → 可选限额 | 企业版基础；规模化版预算控制 |
| 质量门禁 | 仅给建议无法约束高风险代码，但 AI 误报又可能阻塞研发 | 项目负责人、质量/安全负责人、平台管理员 | 先影子计算 → 观察误报/可用性 → 启用警告 → 受控阻断 → 授权旁路/超时熔断 → 全程审计 | 核心版影子；规模化版强制 |
| 全量/Push 扫描 | MR 增量审查无法发现历史存量或非 MR 变更 | 项目负责人、质量负责人、平台管理员 | 建立扫描范围/基线 → 资源评估 → 手动/定时执行 → 存量问题入账 → 与 MR 指标分开 → 增量复扫 | 规模化版 |
| 多平台与生态 | 企业可能存在多套 Git 平台或需向安全平台交换结果 | 平台管理员、质量负责人 | 根据真实需求选第二平台 → 实现能力声明/契约 → 沙箱验收 → 逐项目迁移；SARIF 单独导出 | 规模化版 / 后续候选 |

边界审计结论：

- PR 描述生成、自由问答、自动补文档、自动改 Changelog 等是 PR 助手能力，不进入 MVP；
- “仓库管理”只管理接入与审查范围，不提供代码浏览、分支管理和合并操作；
- “问题台账”不替代 Jira/禅道等工单系统，后续如需协同只做关联和状态同步；
- 自动降级必须显式记录实际执行路径，并验证两条路径的结果口径可比较；
- 个人统计只服务本人自查或经授权辅导，不展示团队个人排行榜；
- Session 仅作为引擎恢复与诊断标识，Session Viewer 不作为近期业务菜单。

## 7. 版本路线图

### 7.1 依赖关系与交付顺序

主依赖链为：

```text
身份/数据范围/凭据安全
  -> 连接与代码项目
  -> Webhook 可信事件
  -> 审查任务骨干
  -> Diff 与审查执行
  -> 问题和审查结论
  -> 平台回写/通知
  -> 整改复核
  -> 指标看板/报告
  -> 强制门禁/规模化扫描
```

规则与模型必须在真实引擎执行前形成最小可用版本；业务审计、幂等和运行 SLI 随每个切片同步建设，不能在链路完成后补。第二 Git Provider、更多通知渠道和全量扫描只能在首条链路稳定后扩展。

MVP 建议按纵向切片交付：连接与项目 → 可信事件 → 任务骨干和可控替身结果 → 真实引擎 → 总结回写 → 单渠道通知 → 基础问题闭环与工作台。每个切片都必须能单独演示失败路径和权限边界。

### 7.2 阶段 0：决策与试点锁定

目标：选定一条可以真实验收的链路，而不是继续扩功能清单。

- 首个 Git 平台已确定为 GitHub，本期只实现 GitHub Personal Access Token 接入；
- 确认 MR/PR 为首个事件，Push 不进入首版；
- 选择 OCR 或内置 LLM 之一作为主执行路径，确定部署、并发、超时和目录配额；
- 确认首个通知渠道、用户映射、代码是否允许发往外部模型、各类数据保留期；
- 确认身份源、凭据主密钥、试点项目和成功指标基线。

验收：决策有责任人和日期；规划、部署说明和实际环境一致；未决项不进入编码。

当前状态（2026-08-01）：Git 平台、项目归属和凭据主密钥来源已随 M1 落地；OCR/内置 LLM、首个通知渠道、代码外发与数据保留期仍待后续切片确认。

### 7.3 MVP（V0.1，内部试点）

## 8. 数据、接口、权限与运行边界

### 8.1 数据与保留

- Webhook 原始载荷、Diff、Prompt、模型原始响应、标准化问题、报告和审计日志分别定义是否保存、脱敏方式和保留期；
- MySQL 保存事件、任务、问题、交付和审计事实，Redis 只做缓存、限流和短期幂等辅助；
- 删除项目不直接物理删除审计证据；停用、归档和依法删除采用不同操作；
- 导出代码片段、问题详情和报告均纳入权限与审计。

### 8.2 接口与外部副作用

- `acr-admin` 只承担 REST/Webhook 协议、校验、权限声明和用例调用；
- Git、审查引擎和通知差异收敛在适配边界，产品用例只依赖统一能力；
- 事件、任务、评论/状态检查、通知分别有唯一键；
- Webhook 接收成功只表示可信事件已持久化，不表示审查完成；
- 不用一个数据库事务包住拉 Diff、模型调用、回写和通知。

### 8.3 最小权限矩阵

| 操作 | 开发者 | 项目负责人 | 质量/安全 | 平台管理员 | 审计人员 |
|---|:---:|:---:|:---:|:---:|:---:|
| 查看授权项目任务/问题 | ✓ | ✓ | ✓ | 按需临时授权 | 只读授权 |
| 处理本人/被指派问题 | ✓ | ✓ | ✓ | - | - |
| 接入项目、重试/取消任务 | - | ✓ | 可选 | ✓ | - |
| 发布规则/审查方案 | - | 项目范围 | 组织范围 | 平台范围 | - |
| 管理模型密钥/连接 | - | - | - | ✓ | - |
| 忽略高风险、门禁旁路 | - | 受控 | 受控 | 紧急受控 | - |
| 查看/导出审计 | 本人相关 | 项目范围 | 授权范围 | 平台范围 | 授权范围 |

高风险忽略、门禁旁路、密钥操作、权限变更、规则发布和审计导出必须二次确认并记录原因；是否需要双人审批在强制门禁版本开始前单独决策，不在首版预建审批引擎。

## 9. 开发准入与阶段决策

以下决策会改变数据、权限或主流程，必须在对应版本编码前确认：

1. 首个 Git 平台、版本、事件类型和测试仓库；
2. 企业身份源，以及部门、业务系统、项目负责人的权威来源；
3. 代码/Diff 是否允许发送到外部模型，各类原始数据是否保存及保留期；
4. 凭据加密主密钥来源、轮换和灾备方式；
5. 首个审查执行路径、OCR 安装位置、并发、超时、工作目录和资源配额；
6. 首个通知渠道、用户映射和紧急联系人；
7. V0.1 是否只回写总结评论；本路线图默认是，inline 评论进入 V0.2；
8. “已关闭”由谁复核；本路线图默认首版人工确认，自动重审后续补充；
9. 内部正式版的可用性、P95 时延、恢复时间、容量和保留期目标；
10. 强制门禁的阈值、旁路人、旁路时限和平台故障策略。

每个版本进入开发前，仍需使用 `skills/plan-review-feature/` 一次只收敛一个可独立验收的纵向切片，明确对象、状态、接口、权限、幂等、外部副作用、失败补偿和验证步骤。
