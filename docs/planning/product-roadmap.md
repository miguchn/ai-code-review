# 代码审查业务产品路线图

## 1. 文档目的

本路线图把根 `README.md` 中 20 项待开发能力收敛成可管理的业务模块、依赖和交付阶段。它是后续需求拆分和范围判断的基线，不代表本次已经实现任何业务功能。

产品目标是形成一条可追踪的企业代码审查闭环：

> 代码事件进入 → 可信接收 → 生成审查任务 → 调用审查引擎 → 保存结果 → 回写代码平台 → 通知相关人 → 跟踪整改 → 汇总质量与成本。

本阶段明确不做：

- 不实现 Webhook、Provider、OCR 调用、通知、审查表或页面；
- 除统一的 `acr-review` 业务边界外，不再拆分其他业务 Maven 模块，也不引入消息队列、工作流引擎或其他基础设施；
- 不一次性为 P1-P3 生成 CRUD；
- 不承诺所有平台同时上线，先按统一契约完成一个平台的纵向闭环。

## 2. 当前基线

### 2.1 已具备

- 用户、角色、部门、菜单、字典、参数、日志、公告、监控和 Quartz 等管理后台能力；
- Vue 3 管理端和 Spring Security + JWT + RBAC；
- `SysBusinessSystem` 的业务系统归属管理，包括部门和负责人；
- `SysAiModelConfig` 的基础配置、启停、默认模型和连接测试；
- `AiClient`、OpenAI 兼容客户端与 Claude 客户端；
- MySQL、Redis、线程池、Quartz 和 Micrometer 基础能力。

### 2.2 仅部分具备

| README 能力 | 当前已有 | 仍缺少 |
|---|---|---|
| 多平台项目接入 | 业务系统及部门归属 | 代码仓库项目、Provider 凭据、平台适配和连通性校验 |
| 模型管理 | CRUD、启停、默认模型、连接测试、展示脱敏 | 加密存储、密钥轮换、Token/超时策略闭环、降级链 |
| 审查引擎 | 内置 LLM 客户端基础 | OCR CLI 契约、结果标准化、超时/重试和降级编排 |
| 定时任务 | 通用 Quartz 管理 | 全量扫描、报告、哨兵等业务任务 |

### 2.3 尚未形成

Webhook 可信接入、审查任务与结果模型、全链路编排、平台回写、通知投递、缺陷流转、规则版本、统计报表和所有 P2/P3 高级能力。

## 3. 业务模块与边界

| 编号 | 业务模块 | 覆盖 README 条目 | 主要职责 | 明确边界 | 前置依赖 | 阶段 |
|---|---|---|---|---|---|---|
| M0 | 基础治理 | 业务系统、模型管理的已有部分 | 组织归属、权限、凭据安全、基础配置 | 不承载仓库事件或审查编排 | 现有 RBAC、部门、AI Client | P0 前置 / P1 完善 |
| M1 | 项目与 Git 接入 | 多平台项目接入 | 仓库项目、平台类型、认证引用、分支策略、业务系统/部门绑定 | 不处理 Webhook 事件，不执行审查 | M0 | P0 |
| M2 | 事件接入 | Webhook 接收 | 平台验签、事件标准化、去重、接收审计、快速响应 | 不在请求线程执行完整审查 | M1 | P0 |
| M3 | 审查执行 | 审查引擎对接 | OCR CLI 调用、JSON 标准化、超时、重试、内置 LLM 降级 | 不决定通知或平台评论样式 | M0、M1 | P0 |
| M4 | 任务与记录 | 审查任务编排、审查记录 | 任务状态、结果、问题项、步骤记录、重试和历史查询 | 不直接调用具体平台 SDK | M1、M2、M3 | P0 |
| M5 | 结果交付 | 结果回写、通知推送 | PR/MR 评论与状态回写，多渠道通知，严重度策略和投递记录 | 不改变审查结论，不维护缺陷业务状态 | M4 | P0 |
| M6 | 质量治理 | 缺陷流转、审查规则、模型管理完善 | 指派/认领、状态流转、误报标记、规则及 Prompt 版本、模型降级链 | 不承担统计报表和主动扫描 | M4、M5 | P1 |
| M7 | 质量洞察 | 数据看板、成员分析、成本统计、日报/周报 | 团队/项目/个人质量、趋势、Token 成本、报告快照 | 只消费已落库事实，不反向修改审查结果 | M4、M6 | P1-P2 |
| M8 | 主动治理与生态 | 全量扫描、Session 回放、项目哨兵、合并卡点、误报回流、SARIF | 定时扫描、主动预警、质量门禁、回放、外部格式和优化反馈 | 每项独立立项，不作为 P0 闭环前置 | M3-M7 | P2-P3 |

代码归属统一为：M0 继续使用 `acr-system` 的平台治理能力，M1-M8 的主要业务实现进入 `acr-review`，REST/Webhook 接入留在 `acr-admin`。业务模块编号只用于产品拆分，不对应新的 Maven 模块。

## 4. 关键依赖关系

主链路依赖为：

`M0 基础治理 → M1 项目接入 → M2 事件接入 → M4 任务编排 → M3 审查执行 → M4 结果落库 → M5 回写/通知`

其中 M3 可以在 M2 之后并行开发，但必须先固定统一输入输出契约。M6 依赖稳定的问题项标识和任务结果；M7 依赖稳定的数据口径；M8 不得提前改变 P0 主链路的模型。

为避免“平台适配做完但链路不可用”，P0 应以纵向切片推进：

1. 选择一个试点平台；
2. 接收一个真实事件；
3. 生成一条任务；
4. 完成一次真实或可控替身的审查；
5. 保存结果；
6. 回写一条评论或状态；
7. 发送一条通知；
8. 在后台查询完整轨迹；
9. 再扩展其余平台。

部署文档当前以 GitLab 为示例，因此建议默认以 GitLab 作为试点，但正式编码前仍需产品确认。

## 5. 建议开发阶段

### 阶段 0：规划与基线锁定

目标：让后续开发有唯一边界。

- 确认试点平台、凭据加密主密钥来源、OCR 安装方式、数据保留期和通知试点渠道；
- 明确首个纵向切片所需对象、状态、API 和包路径；
- 纠正初始化脚本与现有模型字段不一致；
- 建立协作规则、规划技能和验收方式。

验收：本目录两份规划互相一致，项目基础构建通过，`acr-review` 中没有提前生成的业务实现。

### 阶段 1：P0 最小闭环

建议顺序：

1. **项目接入基础**：仓库项目、Provider 契约、试点平台认证与连通性验证；
2. **Webhook 可信接入**：验签、事件标准化、事件唯一键、快速响应；
3. **任务与记录骨干**：任务/结果/问题项及状态流转，先不做复杂查询；
4. **OCR 引擎适配**：安全进程调用、JSON 标准化、超时、失败分类；
5. **主流程编排**：拉 Diff → 执行审查 → 落库，支持从安全步骤重试；
6. **结果回写**：试点平台普通评论优先，再做 inline 评论与状态检查；
7. **通知投递**：先一个渠道，再扩展严重度、@提交者和聚合去重；
8. **管理端查询**：项目、任务列表、任务详情和问题项查看；
9. **扩展平台**：用契约测试依次接入 GitHub、Gitee、Gitea。

阶段验收：

- 同一事件重复投递不会产生重复任务或重复外部副作用；
- 失败可定位到具体步骤并从安全位置重试；
- 从事件到任务、结果、回写和通知均有统一关联标识；
- 凭据不明文返回或记录；
- 至少一个平台、一个通知渠道完成真实沙箱或测试仓库闭环；
- 后端、前端构建通过，关键状态、幂等和失败分支有测试。

### 阶段 2：P1 治理闭环

建议顺序：

1. 缺陷指派、认领、修复、忽略和误报；
2. 模型配置加密、降级链、Token/超时策略；
3. 项目规则、Prompt、规则库共享和版本；
4. 数据看板；
5. 成员分析。

阶段验收：

- 问题状态只有合法流转且有操作者、时间和原因；
- 每次审查能追溯到模型、规则及 Prompt 版本；
- 看板指标可从审查记录重算，列表与图表口径一致；
- 数据权限延续部门、角色和业务系统边界。

### 阶段 3：P2 规模化

建议顺序：

1. Token 成本与项目配额；
2. 日报/周报及定时推送；
3. 全量扫描与仓库存储隔离；
4. 项目哨兵；
5. 合并卡点；
6. Session 回放。

阶段验收：

- 批量和定时任务具备并发、磁盘、超时和失败恢复边界；
- 合并卡点具备旁路/熔断机制，平台异常不造成不可恢复阻塞；
- 成本可按任务、项目、模型和时间范围对账；
- 回放遵循代码资产权限，不跨项目泄露内容。

### 阶段 4：P3 生态优化

先实现误报数据闭环，再评估自动规则/Prompt 优化；SARIF 作为独立导出适配，不改变内部结果模型。

阶段验收：

- 误报回流可追溯、可撤销，未经审批不自动改变生产规则；
- SARIF 输出通过目标平台校验，严重度和位置映射有契约测试。

## 6. 模块级验收口径

| 模块 | 最低验收标准 |
|---|---|
| 项目与 Git 接入 | 项目唯一性、业务系统/部门归属、凭据引用和连通性结果明确；禁用项目不接收任务 |
| Webhook | 支持验签失败、未知项目、重复事件、无关事件和正常事件；响应与最终任务状态解耦 |
| 审查引擎 | 输入输出版本化；超时、非零退出、非法 JSON、超大输出和降级均可测试 |
| 任务与记录 | 任务、结果、问题项关系稳定；状态不可跳跃；步骤错误和重试次数可查询 |
| 结果回写 | 普通评论、inline 评论和状态检查能力按平台声明；重复执行不重复发布 |
| 通知 | 渠道、模板、严重度、收件人和投递状态可审计；重复触发可聚合或跳过 |
| 缺陷流转 | 指派与状态历史完整；忽略/误报必须记录原因和权限 |
| 模型与规则 | 密钥加密；模型和规则版本可追溯；默认项和降级顺序无歧义 |
| 看板与报告 | 指标定义、时间口径、过滤维度和数据权限一致；可回查原始任务 |
| 高级能力 | 每项独立开关、失败隔离和权限边界，不降低 P0 主链路可用性 |

## 7. 开发前必须确认的产品决策

以下问题会改变实现，应在对应阶段开始前确认：

1. 试点 Git 平台及最低支持版本；
2. 首个通知渠道和 @用户映射来源；
3. 是否保存 Webhook 原始载荷、Diff、Prompt、模型原始响应，以及各自保留期；
4. 凭据加密主密钥由环境变量、部署密钥服务还是其他现有机制提供；
5. OCR CLI 的安装位置、允许并发、单次超时和仓库工作目录配额；
6. P0 回写先支持普通评论还是必须首期支持 inline 评论；
7. “已修复”的判定由人工确认、后续提交匹配还是重新审查；
8. HIGH 问题的合并卡点是强制还是可配置。
