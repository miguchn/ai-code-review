# 问题台账审查记录上下文 P0/P1 设计

> 状态：已实现并完成自动化验证（2026-08-09）。本切片不含数据库结构变更。

## 1. 背景与目标

一次审查任务可能识别多条问题，而同一问题又可能跨多次审查持续存在。当前问题台账以“问题”为行，能够完成确认、忽略、复核和关闭，但存在三类阅读与追溯缺口：

- 从审查记录进入问题台账时，仅按 PR 或分支筛选，容易混入其他审查轮次的问题；
- 列表中的首次/最近任务仅显示编号，不能明确表达“同一次审查”和“跨轮持续”的关系；
- 详情能够操作状态，但发现、处置、复核、关闭及关联代码上下文没有形成完整的阅读链路。

本次目标是在不重建现有任务、记录、问题数据体系的前提下，补齐审查记录上下文和问题生命周期表达，提升问题的可追溯性、可管理性和阅读效率。

成功标准：

1. 从任一已结束审查记录进入问题台账，只展示该记录实际产出的、已进入台账的问题；
2. 用户可在列表和详情中识别问题编号、首次发现审查记录、最近审查记录及当前生命周期阶段；
3. 用户可按审查记录、发现时间、分支和 PR 发起人筛选；
4. 详情能够串联项目、PR/Push、分支、提交、发现、处置、复核和关闭信息；
5. 兼容现有问题确认、忽略、复核、关闭、批量处置及旧审查记录查询链路。

## 2. 产品边界

### 2.1 本次范围

- 新增“按审查记录查看”的问题台账上下文；
- 问题列表补充审查记录、发现时间、分支、PR 发起人筛选；
- 调整列表字段和文案，明确问题编号、变更来源、审查轨迹和生命周期状态；
- 增强详情的代码上下文、首次/最近审查记录、阶段说明和时间线事件类型；
- 审查记录详情跳转问题台账时携带精确审查记录标识；
- 补充接口、测试、场景验证及规划文档。

### 2.2 明确不做

- 不新增“审查批次”表：现有 `review_task.task_id` 已能唯一标识一次审查记录；
- 不改变问题跨轮去重模型：问题仍按 PR/分支上下文和指纹持续跟踪；
- 不新增负责人、认领、转派、催办、逾期或通知能力：这些能力需要完整的权限、审计和通知闭环；
- 不新增“处理中”状态：当前系统尚无可验证的开始处理动作，避免产生名义状态；
- 不改动扫描、Webhook、重试、投递和问题处置的既有主链路。

## 3. 核心设计决策

### 3.1 审查记录标识

复用 `taskId` 作为审查记录编号，页面统一显示为“审查记录 #ID”。任务执行中是审查任务，任务结束后是可追溯的审查记录，两者共享同一实体，不再创造平行编号。

### 3.2 审查记录与问题的精确关联

问题实体的 `firstTaskId`、`lastTaskId` 用于表达首次发现和最近出现，不能代表中间任一审查记录的完整问题集合。因此，“按审查记录查看”不使用 `firstTaskId/lastTaskId` 反推，而使用该记录成功运行结果中的 Top Issues，并通过既有问题指纹补充的 `issueId` 关联台账。

该方案具有以下特性：

- 精确：展示的是该次运行实际产出的结果问题；
- 兼容：不改变问题表和问题生成链路；
- 可解释：历史记录中尚未物化为台账问题的结果单独提示，不伪装为已跟踪问题；
- 可扩展：后续如需要全量问题快照，可在不改变页面契约的情况下增加持久化关联表。

### 3.3 生命周期语义

页面沿用现有状态，不新增虚假阶段：

| 状态 | 页面语义 | 用户关注点 |
| --- | --- | --- |
| 待确认 | 系统发现，等待人工确认是否纳入治理 | 确认或忽略 |
| 待修复 | 已确认，等待代码修复 | 修复后等待下一次审查 |
| 待复核 | 新代码中疑似已消失，等待人工验证 | 关闭或恢复 |
| 已关闭 | 已验证修复、误报或人工关闭 | 查看关闭来源和时间 |

“待复核”必须明确为“疑似已修复、待人工验证”，避免用户将其误解为系统已经确认修复。汇总卡片“需处理”调整为“待人工处置”，口径仍为“待确认 + 待复核”。

## 4. 数据与接口设计

### 4.1 数据结构

本次不新增数据库字段，仅扩展查询模型和详情返回：

- `ReviewIssue` 查询条件：`reviewTaskId`、`prAuthor`、`branchKeyword`；
- `ReviewIssue` 列表展示字段：业务系统、事件来源、PR 标题/发起人、源/目标分支、提交 SHA、仓库坐标、首次/最近审查时间；
- `ReviewIssueDetail`：增加首次发现审查记录、最近审查记录；保留原来源任务字段以兼容现有调用；
- `ReviewIssueRecordContext`：审查记录、采用的成功运行、已跟踪问题、未跟踪结果问题、结果问题数。

列表展示字段通过问题关联的项目及首次/最近任务查询得到，不写回问题表，避免复制易变化的任务上下文。

### 4.2 接口

- 保留 `GET /review/issue/list`：普通问题台账分页查询；
- 新增 `GET /review/issue/record/{taskId}`：按审查记录返回精确问题上下文；
- 保留 `GET /review/issue/{issueId}`：详情返回增加首次/最近审查记录；
- 现有状态变更和批量处置接口保持不变。

记录上下文接口选择该任务最新一次成功运行。任务不存在、未结束或无访问权限时拒绝访问；已结束但无成功运行时返回记录上下文和空问题集合。

### 4.3 权限与数据范围

- 查询沿用 `review:issue:list` 权限；
- 继续使用项目所属部门和项目负责人数据范围；
- 记录上下文先校验任务所属项目，再对问题列表应用同一数据范围；
- 不允许通过 taskId 绕过项目访问边界。

## 5. 页面与交互设计

### 5.1 普通问题台账

- 查询区增加审查记录编号、分支、PR 发起人和发现时间；
- 标题列显示“问题 #ID”，便于沟通、检索和工单引用；
- “合并请求”调整为“变更来源”，兼容 PR 与 Push；
- “轮次轨迹”调整为“审查轨迹”，使用“首次 #ID → 最近 #ID”明确含义；
- 同时呈现首次发现时间和最近变更时间；
- 汇总卡片使用“待人工处置”，并提示其统计口径；
- 状态标签继续使用中国大陆企业系统常见的明确中文动作语义。

### 5.2 按审查记录查看

从审查记录详情进入后，问题台账顶部展示上下文卡片：

- 审查记录编号、项目/业务系统；
- PR 标题或 Push 分支、发起人、源/目标分支；
- 本次提交、审查结论、完成时间、结果问题数；
- “查看审查记录”“打开 PR”“退出记录视图”快捷操作。

此模式只展示该记录实际结果中已关联台账的问题，不显示全局统计，不与其他轮次混排。历史结果中存在未进入台账的问题时显示说明，避免用户误认为数据丢失。

### 5.3 问题详情

- 标题使用“问题 #ID · 问题标题”；
- 顶部展示当前状态解释，待复核状态突出“疑似已修复、待人工验证”；
- 上下文区展示项目、业务系统、PR/Push、发起人、分支、提交、发现时间、阶段进入时间和关闭信息；
- 审查关联拆分为“首次发现审查记录”和“最近审查记录”，支持跳转；
- 时间线使用“系统事件/人工处置”标签，降低自动扫描事件与人工操作混淆；
- 现有处置、复核证据和投递信息保持原位置与操作逻辑。

## 6. 兼容性与演进

- 对旧记录：运行结果无法关联 `issueId` 的问题列入“未跟踪结果”，不自动创建或修改问题；
- 对失败记录：仍可查看记录上下文，但没有成功运行结果时不展示问题；
- 对 PR/Push：统一使用“变更来源”，PR 可打开外部链接，Push 保留分支/提交追溯；
- 对后续指派能力：未来应以独立指派记录承载负责人、时间、操作人和变更历史，而非仅在问题表增加负责人字段；
- 对后续快照能力：当单次结果超过当前 Top Issues 范围或需要审计级快照时，可增加任务-问题关联快照，保持现有接口和页面不变。

## 7. 验收场景

1. 同一 PR 连续两次审查，第二次只包含部分历史问题；从两条记录分别进入台账，问题集合与各自运行结果一致；
2. 一个问题跨多轮存在，列表和详情能显示首次发现与最近审查记录；
3. 问题进入待复核时，页面明确提示需要人工验证，关闭或恢复操作保持可用；
4. 按审查记录、发现时间、分支、PR 发起人组合筛选能得到正确结果；
5. Push 记录没有 PR 编号时，仍能展示分支、提交及对应问题；
6. 历史结果无法关联问题台账时，页面提示未跟踪数量，不混入可处置列表；
7. 无项目访问权限的用户不能通过审查记录编号查看上下文；
8. 现有单条处置、批量处置、复核、关闭和记录详情链路无回归。

## 8. 验证计划

- 服务单元测试：成功运行选择、结果问题顺序、未跟踪结果、无成功运行、未结束任务、详情首次/最近记录；
- 接口与数据范围检查：记录上下文权限、项目范围和普通筛选；
- 前端生产构建：确保新增查询、上下文卡片和详情组件可编译；
- 场景核验：PR、Push、跨轮问题、失败记录和历史未跟踪结果。

### 8.1 实施验证结果（2026-08-09）

- 后端全量测试：508 例通过，0 失败、0 错误、0 跳过；
- 问题服务专项测试：41 例通过，覆盖记录结果顺序、历史未跟踪、失败记录、越权拒绝和快照写入失败隔离；
- 前端生产构建通过；
- Mapper XML 语法检查与代码差异格式检查通过。
