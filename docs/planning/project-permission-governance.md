# 项目级权限与敏感资产治理

更新时间：2026-08-12  
状态：已实施，待存量环境执行 `sql/45_project_permission_governance.sql`

## 1. 目标与结论

本次在既有菜单/按钮 RBAC 和部门 `DataScope` 上增加项目授权边界，不替换现有权限体系。最终访问判定为：

> 有效权限 = 功能权限（RBAC） × 组织数据范围（DataScope） × 项目成员角色

超级管理员保留全局旁路。普通用户即使与项目同部门、持有相同菜单权限，只要不是项目负责人或有效项目成员，也不能查看该项目、任务、审查记录、问题、投递记录和洞察数据。

平台敏感资产采用独立的角色层级：Git 凭据、通知渠道、审查模板、模型配置和审查引擎接口的权限字符串，必须由同一个有效的“平台级角色”授予；部门级角色即使误配了相同权限字符串，也不能获得全局资产管理能力。

## 2. 基线问题与影响范围

实施前主要依赖部门数据范围，存在三类风险：

1. 同部门不同项目默认互相可见，代码变更、任务、结论和问题台账缺少项目隔离；
2. 列表受 `DataScope` 控制，但若按 ID 的详情或动作接口只查主键，可能绕过列表范围；
3. 凭据、模型、通知渠道和模板是平台全局资产，普通部门角色误勾菜单权限后可以访问或维护；项目表单直接调用敏感资产列表，也扩大了暴露面。

本次覆盖代码项目、任务、审查记录、问题台账、投递记录、工作台、数据洞察，以及项目对凭据/模型/模板/通知渠道的引用。Webhook、调度器和审查执行器属于内部可信调用链，不套用当前交互用户的项目成员判断。

## 3. 授权模型

### 3.1 项目角色

| 项目角色 | 查看项目数据 | 重试/取消任务、处置问题、补发投递 | 编辑项目、测试连接、管理成员 | 转移负责人、删除项目 |
|---|:---:|:---:|:---:|:---:|
| OWNER（负责人） | ✓ | ✓ | ✓ | ✓ |
| ADMIN（项目管理员） | ✓ | ✓ | ✓ | - |
| REVIEWER（审查处理人） | ✓ | ✓ | - | - |
| VIEWER（只读成员） | ✓ | - | - | - |

项目负责人由 `review_project.owner_user_id` 表示，不重复写入成员表；其他成员写入 `review_project_member`。成员必须处于启用状态。项目 ADMIN 可以维护 ADMIN/REVIEWER/VIEWER，不能创建第二个 OWNER；负责人变更仍走项目编辑并只允许当前负责人或超级管理员执行。

部门范围和项目成员采用交集语义：被加入项目不意味着可以越过组织数据范围访问其他部门。这保留了现有企业组织授权边界，也避免项目成员关系成为跨部门提权通道。

### 3.2 平台角色

`sys_role.role_scope` 取值：

- `PLATFORM`：可承载平台敏感资产权限，仅超级管理员可创建、编辑、授权、停用或删除；
- `DEPARTMENT`：承载普通功能和部门数据权限，不能通过敏感资产权限字符串获得平台能力。

平台权限按“同一角色同时满足角色层级和权限字符串”校验，不能把一个部门角色的权限字符串与另一个平台角色拼接后生效。普通用户管理员也不能编辑、停用、重置密码、删除或重新授权持有平台角色的用户。

### 3.3 项目引用平台资产

项目页面不再调用敏感资产管理列表。只有具备对应平台权限的角色才会收到凭据、模型、模板或通知渠道的全量脱敏选项（ID、名称、类型）；普通项目成员仅能从项目详情看到当前已绑定项，不能枚举平台资产清单。绑定或变更资产时，后端仍校验对应平台级查询权限；只有项目角色、没有平台资产权限的用户可以维护项目的一般策略，但不能换仓库/凭据、模型、模板或通知渠道。

已有项目的当前凭据可用于项目管理员执行连接测试，服务端不返回密文；读取任意新仓库或改用其他凭据必须先通过平台级凭据权限校验。

## 4. 接口与数据隔离

列表类查询在原部门 `DataScope` 之后叠加“负责人或有效成员”条件，覆盖项目、任务、记录、问题、投递、工作台和洞察的列表、统计、趋势与下钻。

按 ID 接口在读取业务对象后，根据其 `project_id` 执行对应项目角色校验，覆盖：

- 项目详情、编辑、启停、连接测试、删除、仓库信息读取；
- 任务详情、重试、取消；
- 审查记录详情；
- 问题详情、记录上下文、确认、关闭、忽略、重开和批量处置；
- 投递详情、正文、任务/问题关联投递、重试和人工处理。

功能权限仍由 Controller 的 RBAC 声明负责；项目授权集中在 `ReviewProjectAccessService`，避免各业务服务重复解释角色。

## 5. 数据迁移与兼容策略

增量脚本 `sql/45_project_permission_governance.sql`：

1. 为 `sys_role` 增加 `role_scope`，超级管理员角色设为 `PLATFORM`；
2. 其他存量角色按最小权限原则设为 `DEPARTMENT`；
3. 创建 `review_project_member` 及项目、用户唯一约束和查询索引。

升级后，原先仅依靠同部门或业务系统负责人身份查看项目的用户会失去项目访问权，需要由项目负责人补录项目成员。这是有意的 fail-close 行为。确需维护凭据、模型、模板或通知渠道的存量角色，必须由超级管理员审查后显式提升为 `PLATFORM`。

## 6. 验收标准

- 同部门 A、B 两项目：A 的非成员不能在列表、统计、详情和动作接口看到或操作 A；
- VIEWER 只读，REVIEWER 可处置，ADMIN 可管理项目与成员，只有 OWNER 可转移负责人和删除；
- 超级管理员仍可查看和管理全部项目；
- 部门角色即使含敏感权限字符串，也不能访问凭据、渠道、模板、模型和引擎接口；
- 平台角色的权限不能被普通角色管理员维护或转授；
- 项目表单不返回任何 Token、Webhook 密钥、模型 API Key 等敏感值；
- 后端单元测试、全量 Maven 测试和前端生产构建通过。

## 7. 明确不在本次范围

- 不引入 ABAC/策略引擎、审批流或新的通用权限中心；
- 不建设跨部门项目协作例外机制；确有业务需求时需单独设计审批、时效和审计；
- 不改变 Webhook、调度器和审查执行器的内部服务身份；
- 不扩展问题指派、质量门禁或审计导出等其他路线图能力。
