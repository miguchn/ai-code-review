## 1. 背景与目标

项目设置中的「审查范围」目前只回答"审哪些文件"（排除路径、测试文件、存量问题、高影响扩展四字段），
不回答"什么行为触发审查"——触发方式被隐含写死为合并请求（PR/MR）一条线。

M10 把「审查范围」升级为「审查配置」，回答两个问题：

1. **审查类型**：这个项目接受哪种触发行为——合并请求审查（现有 PR/MR 线）和/或推送审查（直接 push 线）；
2. **审查范围**：针对所选审查类型，分别配置"审哪些"。

目标：不走 PR 合并流程的团队（直接向 main/develop 推送）也能把仓库接入 ACR；
走 PR 的团队配置体验不变。

## 2. 两种审查类型定义

| 维度 | 合并请求审查（现有线） | 推送审查（新线） |
|---|---|---|
| 触发事件 | PR/MR opened / reopened / synchronize | push 到配置的触发分支（before/after 增量） |
| 审查时机 | 合并前 | 合并后（不做合并前拦截） |
| Diff 来源 | PR base...head | push before...after |
| 结果交付 | PR 评论（原地更新）+ 台账 | commit 评论 / IM 通知 + 台账（无 PR 评论可挂） |
| 问题台账 | 复用（fingerprint 按 project+PR；push 线按 project+分支归组，见 §6 待决） | 复用 |
| 引擎/验签/凭据 | 复用 | 复用 |

推送线边界（继承 §7.6 已确认口径）：**只做合并后审查**——发现、通知、台账处置；
不做质量门禁、不阻断推送。

## 3. 页面形态：项目设置「审查配置」区

原「审查范围」卡片升级为「审查配置」，两个分区自上而下排列。

### 3.1 审查类型（上区）

两个带说明文案的选项卡片（checkbox 或 radio，见 §5 待决）：

- **合并请求审查**
  提示文案：`在合并请求（PR/MR）创建或更新代码时触发审查，审查结论以合并请求评论发布，问题进入问题台账。适合有合并请求协作流程的团队。`
- **推送审查**
  提示文案：`代码直接推送到指定分支（不经合并请求）时触发审查，审查结论以提交评论或通知送达，问题进入问题台账。适合直接向主干推送代码的团队。本审查为推送后审查，不拦截推送。`

至少选择一项；未选时保存阻断并提示「请至少选择一种审查类型」。

### 3.2 审查范围（下区，随审查类型联动）

**公共字段**（所选任一类型都展示）：

| 字段 | 现状 | 说明 |
|---|---|---|
| 排除路径 glob | review_project.exclude_paths | 不变 |
| 审查测试文件 | include_test_files（默认 N） | 不变 |
| 上报历史存量问题 | report_legacy_issues（默认 N） | 不变 |
| 高影响变更扩展整文件 | expand_high_impact_files（默认 Y） | 不变 |

**类型专属字段**：

- 勾选合并请求审查 → 展示「目标分支」（现有字段平移，控制哪些 PR 目标分支进入审查）
- 勾选推送审查 → 展示「触发分支」（必填，换行分隔的分支名或通配，如 `main`、`develop`、`release/*`；
  默认建议值 main）+ 提示文案：`仅列出的分支上的推送会触发审查，其余分支推送忽略。`

两种类型都勾选时，专属字段各自成组展示，公共字段只出现一份。

## 4. 数据模型影响（评估级，开发前细化）

- review_project 增审查类型字段（如 `review_types`，逗号分隔 `PR,PUSH` 或两布尔列——开发话术阶段定）；
  存量项目默认 `PR`，行为与升级前完全一致（零迁移风险口径）
- 推送线复用四平台适配器的 push 事件解析（部分平台已有雏形），任务模型需区分事件来源
  （review_task 增来源类型列，区分 PR 任务与 PUSH 任务）
- 台账 fingerprint 唯一键当前含 pr_number；push 线无 PR，归组键方案见 §6 待决

## 5. 待产品决策：审查类型单选还是多选

**方案 A：单选**

- 优点：配置最简单，一个项目一种模式，心智负担小；触发判断无歧义
- 缺点：同一仓库无法两种模式并存。review_project 以仓库为粒度（repository_full_path 唯一），
  单选下"主干走 PR、hotfix 直推"的混合团队只能重复建项目指向同一仓库，数据模型失真

**方案 B：多选（推荐）**

- 优点：覆盖混合协作模式；与 roadmap §7.6「与 PR 事件并存」的既定方向一致；
  存量项目默认仅勾选合并请求，升级无感
- 代价：审查范围需按类型分组展示（§3.2 已设计）；需明确"同一合并动作可能同时触发两条线"的口径
  （PR 合并时平台会发 push 事件——推送线对合并结果做一次推送后审查是预期行为，不是重复审查：
  PR 线负责合并前发现与关闭联动，推送线负责合并后兜底）

**推荐 B**，理由即上；若产品侧判断试点团队均为单一模式，A 也能接受，但 review_types 字段建议
仍按可多选设计存储，UI 用单选控件，避免日后返工。

## 6. 待决问题清单

1. 审查类型单选/多选（§5，推荐多选）
2. push 线台账归组键：无 pr_number，fingerprint 唯一键 `(project_id, pr_number, fingerprint)`
   如何扩展（pr_number 哨兵值 vs 增 branch 维度键）——影响 M8 对账逻辑，需单独设计评审
3. push 线交付渠道：commit 评论四平台 API 支持度参差（GitHub/GitLab/Gitea 支持 commit comment，
   Gitee 受限），受限平台降级为 IM 通知 + 台账，是否接受
4. M10 是否拆两个切片交付：M10.1 审查配置形态与数据模型（push 选项可先保存但标注「即将上线」），
   M10.2 推送执行线最小可用；还是不拆一次交付。推荐拆——配置形态先行风险低

## 7. 验收（决策后细化）

- 存量项目升级后审查行为与升级前一致（默认仅合并请求线）
- 新建项目可配置两种审查类型并分别保存审查范围
- 推送审查端到端：推送触发任务 → 审查 → commit 评论/通知 → 台账可见
- 页面提示文案与 §3 一致
