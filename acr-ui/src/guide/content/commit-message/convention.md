# 提交注释规范说明

这篇帮你了解平台如何使用你的 commit 注释（commit message），以及怎样写注释能让审查结果更准。

## 平台如何读取 commit 注释

审查时，平台会把合并请求的 commit 注释作为上下文提供给模型，读取规则如下（GitHub / GitLab / Gitee / Gitea 四平台一致）：

| 规则 | 说明 |
|---|---|
| 每个 PR 最多取 30 条 | 超过 30 个 commit 时只取前 30 条，末尾附「... 另有 N 个提交未展示」 |
| 每条只取首行 | 注释正文（首行换行之后的内容）不进入审查上下文 |
| 单行最长 500 字符 | 超长首行截断到 500 字符并以 `...` 结尾 |

也就是说：**模型看到的只是每个 commit 的首行摘要**，首行写清楚意图，审查模型才能结合代码变更理解你的目的。

## 审查范围与注释的关系

平台默认**只审查本次合并请求变更的内容**（Diff 变更行），不扫描整个文件的历史问题，存量问题不会被打标上报；锁文件、依赖目录与构建产物由平台统一排除。

因此「小步提交 + 注释说清意图」的 PR 审查效果最好：变更集中、每笔提交目的明确，模型更容易判断改动是否符合预期。

## 注释写作建议

1. **首行 ≤50 字符，自包含意图**：类型 + 范围 + 做了什么，例如 `fix: 修复台账列表分页越界导致的重复数据`；
2. **使用 Conventional Commits 前缀**：`feat`（新功能）、`fix`（缺陷修复）、`refactor`（重构）、`docs`（文档）、`test`（测试）、`chore`（杂务）、`perf`（性能）；
3. **一个 PR 控制在 30 个 commit 以内**：超出先 squash 整理再发起合并请求，避免注释被截断丢失；
4. **正文换行写动机与影响面**：正文虽不进入审查上下文，但对人工评审和 `git log` 追溯很重要；
5. **避免无信息注释**：「修 bug」「更新」「WIP」「1」这类注释无法帮助模型判断意图，等于浪费上下文。

正误对照与可复制模板见「提交注释规范 → 注释正误实例对照」。
