# 注释正误实例对照

这篇用对照实例说明什么样的 commit 注释能帮平台给出更准的审查结论，文末提供可直接复制的模板。

## 对照实例

| 不推荐 | 推荐 | 为什么更好 |
|---|---|---|
| `修 bug` | `fix: 修复台账列表分页越界导致的重复数据` | 说清了修的是什么缺陷、什么现象，模型能对照代码判断修复是否完整 |
| `更新` | `docs: 更新部署文档中的 Webhook 回调地址说明` | 「更新」没有信息量；加上类型与对象后意图明确 |
| `优化代码` | `refactor: 抽取四平台 Webhook 验签公共逻辑到适配器` | 说明了重构的手段与范围，便于识别行为是否应保持不变 |
| `添加接口` | `feat: 新增投递记录手动补发接口，支持投递失败后重发` | 说明了新增能力的用途，模型可检查接口设计与命名是否匹配 |
| `WIP` | `feat: 钉钉渠道支持加签校验`（开发中的 WIP 提交在合并前先 squash 整理） | WIP 提交不应直接进入目标分支；整理后的注释才具备审查价值 |
| `fix bug` | `fix: 修复审查任务并发重试时令牌过期未刷新的问题` | 英文套话同样没有信息量；具体到模块与根因才有帮助 |
| `test` | `test: 补充提交注释截断逻辑的边界用例` | 说明测试覆盖的对象，避免被误认为无意义提交 |
| （一行超长注释，200+ 字） | 首行写摘要（≤50 字符），细节换行写正文 | 平台只取首行进入审查上下文，超长首行会被截断到 500 字符 |

规律：前缀表明类型，主语表明对象，动词表明做了什么；三者齐备就是一条好注释。

## 可复制模板

```text
feat(模块): 简要说明新增的功能

动机与影响面：
- 为什么做这个改动
- 影响哪些既有行为/接口
```

```text
fix(模块): 简要说明修复的缺陷现象

根因与验证：
- 缺陷根因一句话
- 如何验证已修复（用例/场景）
```

```text
refactor(模块): 简要说明重构方式与范围

说明：
- 行为是否保持不变
- 需要同步调整的调用方/配置
```

> 模板中的正文部分供人工评审与 git log 使用；进入审查上下文的是首行，请把最关键的信息放在首行。
